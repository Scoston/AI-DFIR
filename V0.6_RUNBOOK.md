# AI-DFIR v0.6 — Automated Containment & Forensic Preservation

## Objective

v0.6 adds a response layer to the v0.5 continuous fleet-attestation system.

The central rule is:

> **Preserve the suspect execution state before changing it whenever operationally possible.**

v0.6 does not default to killing processes, deleting adapters, or rewriting model weights. Instead it uses a signed containment control that the inference/tool execution path enforces.

This provides proportional containment while preserving the evidence required to determine what happened.

---

# Containment modes

```text
observe
    Evidence/alert only.

freeze-tools
    Model inference allowed.
    ALL tool execution denied.

read-only
    Model inference allowed.
    Only operator-approved non-mutating tools allowed.

quarantine
    New local inference denied.

failover
    Suspect local inference denied.
    Requests are directed to an approved fallback backend.

released
    Containment removed after the signed recovery gate succeeds.
```

The production inference worker/router must integrate `ContainmentGuard`.

See:

```text
containment_integration_example.py
```

---

# Two-phase containment transaction

```text
CRITICAL EVENT
     |
     v
SIGNED CONTAINMENT PLAN
     |
     v
PRE-CONTAINMENT PRESERVATION
     |
     +-- runtime/process evidence
     +-- model/runtime manifests
     +-- activation evidence
     +-- canary results
     +-- hardware-attestation evidence
     +-- configured case artifacts
     |
     v
SIGNED EVIDENCE SEAL
     |
     v
APPLY SIGNED CONTAINMENT CONTROL
     |
     v
POST-CONTAINMENT PRESERVATION
     |
     v
HASH-CHAINED CONTAINMENT AUDIT
```

By default:

```text
pre-preservation fails
        |
        v
containment transaction ABORTS
```

This protects forensic completeness.

For incidents where containment must take priority, a signed plan can explicitly set:

```text
preservation_failure_action = contain_anyway
```

That override is recorded in the containment audit.

# 2. Create separate response identities

Recommended separation:

```text
response-plan key
    signs proposed containment plans

approver key
    independently authorizes plans/releases

containment key
    signs controls consumed by model/tool workers

investigator key
    signs forensic evidence bundles
```

Create each using:

```bash
python fleet_crypto.py keygen \
  --private <role>.pem \
  --public <role>.pub.pem
```

Do not put all private keys on the inference worker.

The containment public key belongs on the worker.

The containment private key belongs in the response/security trust domain.

# 3. Integrate the containment guard

Example:

```python
from containment_guard import ContainmentGuard

guard = ContainmentGuard(
    "/run/ai-dfir/containment.json",
    "/etc/ai-dfir/containment_ed25519.pub.pem",
    fail_closed=True,
)
```

Before local inference:

```python
guard.allow_inference()
```

Before a tool call:

```python
guard.authorize_tool(
    "lookup_ticket",
    mutating=False,
)
```

At a request router:

```python
backend = guard.routing_target(
    default_backend="http://qwen-prod-01:8000"
)
```

## Important

The tool's `mutating` classification must come from an operator-controlled tool registry.

Do not allow the model to decide whether its own tool call is "read only."

# 4. Manually create a containment plan

Example:

```bash
python containment_plan.py create \
  --private-key response_plan.pem \
  --incident-id AIIR-001 \
  --node-id qwen-prod-01 \
  --alert-id 438 \
  --mode freeze-tools \
  --reason "Unexpected runtime hook detected" \
  --out containment_plan.json
```

For read-only containment:

```bash
--mode read-only \
--read-only-tool lookup_ticket \
--read-only-tool search_logs
```

For failover:

```bash
--mode failover \
--approved-backend https://approved-qwen.internal
```

# 5. Independent approval

```bash
python containment_plan.py approve \
  --plan-public-key response_plan.pub.pem \
  --plan containment_plan.json \
  --approver-private-key responder_approver.pem \
  --out containment_approval.json
```

Verify:

```bash
python containment_plan.py verify \
  --plan-public-key response_plan.pub.pem \
  --plan containment_plan.json \
  --approver-public-key responder_approver.pub.pem \
  --approval containment_approval.json
```

The approval binds cryptographically to the exact plan payload.

Changing the plan after approval invalidates that approval.

# 6. Execute containment

```bash
python execute_containment.py \
  --plan containment_plan.json \
  --plan-public-key response_plan.pub.pem \
  --require-approval \
  --approval containment_approval.json \
  --approver-public-key responder_approver.pub.pem \
  --case-dir /evidence/AIIR-001 \
  --containment-private-key containment.pem \
  --containment-public-key containment.pub.pem \
  --control-file /run/ai-dfir/containment.json \
  --preservation-signing-key investigator.pem \
  --pid <MODEL_PID> \
  --model-path /srv/models/qwen38 \
  --copy runtime_inventory=/var/lib/ai-dfir/model_runtime_inventory.json \
  --copy live=/var/log/ai-dfir/live \
  --reference deployed_manifest=/var/lib/ai-dfir/deployed_manifest.json
```

Outputs include:

```text
pre_preservation/
    evidence/
    preservation_manifest.json
    signed_seal/

post_preservation/
    evidence/
    preservation_manifest.json
    signed_seal/

containment_audit.jsonl
EXECUTION_RESULT.json
```

# 7. Optional process-memory preservation

Process memory may contain:

```text
prompts
retrieved context
credentials/tokens
decrypted model material
tool results
user data
```

Treat it as highly sensitive evidence.

Opt-in Linux acquisition:

```bash
sudo bash collect_process_memory_linux.sh \
  --pid <MODEL_PID> \
  --out /evidence/AIIR-001/process_memory \
  --min-free-gb 64
```

Requirements:

```text
gcore
sufficient storage
incident authorization
appropriate privacy/data-handling controls
```

The collector never enables memory acquisition automatically.

# 8. Automatic responder

Start with:

```text
auto_responder_config.example.json
```

Modes:

```text
dry-run
approval
auto
```

Recommended first production mode:

```json
"automation_mode": "approval"
```

Run:

```bash
python auto_responder.py \
  --config /etc/ai-dfir/auto_responder.json
```

The responder polls:

```text
GET /v1/alerts
```

and maps explicit finding codes to operator-defined containment modes.

Example:

```text
UNEXPECTED_RUNTIME_HOOK
        -> failover

MODEL_CONTENT_TREE_DRIFT
        -> quarantine

ACTIVATION_DRIFT_CRITICAL
        -> freeze-tools

DELEGATED_AUTHORITY_DRIFT
        -> freeze-tools
```

The mapping is policy, not model judgment.

# 13. Decision/consequence containment

Isolating the model does not undo actions already performed.

Examples:

```text
account disabled
credential revoked
ticket changed
email sent
database record modified
delegated agent launched
```

Run:

```bash
python consequence_reconciler.py \
  --trace agent_trace.jsonl \
  --out open_consequences.json
```

It identifies consequence events that have no corresponding containment/remediation event.

A containment trace can close an effect with:

```json
{
  "event_type": "containment",
  "metadata": {
    "closes_event_id": "<consequence event id>"
  }
}
```

This creates a downstream remediation queue.

# 14. Recovery is a separate signed transaction

Do not simply delete:

```text
/run/ai-dfir/containment.json
```

That destroys provenance and bypasses approval.

Create a signed release request:

```bash
python recovery_gate.py request \
  --private-key release_request.pem \
  --incident-id AIIR-001 \
  --node-id qwen-prod-01 \
  --control-file /run/ai-dfir/containment.json \
  --check model_hash_clean=true \
  --check runtime_inventory_clean=true \
  --check canary_clean=true \
  --check fleet_state_clean=true \
  --out release_request.json
```

Independent approval:

```bash
python recovery_gate.py approve \
  --request-public-key release_request.pub.pem \
  --request release_request.json \
  --approver-private-key incident_commander.pem \
  --out release_approval.json
```

Release:

```bash
python recovery_gate.py execute \
  --release-request release_request.json \
  --request-public-key release_request.pub.pem \
  --release-approval release_approval.json \
  --approver-public-key incident_commander.pub.pem \
  --containment-private-key containment.pem \
  --containment-public-key containment.pub.pem \
  --control-file /run/ai-dfir/containment.json \
  --open-consequences open_consequences.json
```

Release is blocked when:

```text
a check failed
OR
downstream consequences remain open
OR
the containment control changed after release approval was requested
OR
the approval does not match the request
```

Overrides exist for exceptional incident-command decisions and are explicit on the command line.

# 15. Evidence integrity

The response workflow produces three independent provenance layers:

```text
Fleet evidence
    signed node heartbeat
    signed collector receipt

Incident evidence
    pre/post preservation bundle
    investigator signature

Containment evidence
    signed plan
    independent approval
    signed enforcement control
    hash-chained audit log
    signed release request/approval
```

This makes it much harder to silently rewrite the history of what happened during containment.

# 16. Recommended operational policy

A reasonable starting posture:

```text
MEDIUM
    observe

HIGH
    read-only / analyst review

CRITICAL behavioral drift
    freeze-tools

CRITICAL model/runtime integrity
    quarantine or approved failover

Evidence chain invalid
    quarantine

Delegated authority unexpectedly expands
    freeze-tools immediately
```

Adjust to the business impact of each AI system.

---

# 17. Safety characteristics

v0.6 intentionally does NOT provide a generic automatic:

```text
iptables isolation
process kill
model deletion
credential destruction
filesystem wipe
```

Those controls are environment-specific and can destroy evidence or create outages.

The framework's native control is **application-level authority containment** through signed policy.

Environment-specific network/process isolation can be integrated as separately approved response adapters if required.

```text
                         SECURITY TRUST DOMAIN

                   +--------------------------+
                   | Fleet Collector          |
                   | Auto Responder           |
                   |                          |
                   | plan signing             |
                   | containment signing      |
                   | evidence signing         |
                   +-------------+------------+
                                 |
                      signed containment
                                 |
                    +------------+------------+
                    |                         |
               AI Worker                 Approved Failover
                    |
          containment PUBLIC key
                    |
           ContainmentGuard
             /          \
        inference       tools
```

Keep the enforcement private key away from the worker being monitored.

# 19. Test before enabling automatic containment

Minimum staging tests:

```text
unexpected adapter
unexpected forward hook
modified model file
activation drift
authority-policy drift
tool-schema drift
collector outage
agent outage
invalid control signature
expired/stale failover
failed preservation
full evidence disk
recovery with open consequences
key rotation
```

`v06_selftest.py` covers the core control-state invariants, but production integrations require environment-specific validation.
