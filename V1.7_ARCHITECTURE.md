# AI-DFIR v1.7.0 — Investigation Assurance & Evidence Integrity

## Status

This document defines the architecture and trust model for AI-DFIR v1.7.0.

The central objective of v1.7 is:

> An AI-DFIR investigation should be independently reconstructable from preserved evidence, provenance records, tool activity, AI involvement, transformations, and analyst decisions.

v1.7 extends the evidence-preservation, investigation, provider-telemetry, agentic-response, and production-assurance capabilities established in earlier AI-DFIR releases. It does not replace those systems with a parallel forensic subsystem.

---

## 1. Design Principles

AI-DFIR v1.7 follows six investigation-assurance principles:

1. **Source evidence remains distinct from derived evidence.**
   Original evidence must not be silently overwritten by normalization, enrichment, AI processing, analyst annotation, or reporting.

2. **Every consequential transformation should be attributable.**
   Derived artifacts should identify their source artifacts, transformation mechanism, relevant tool or component, and resulting integrity identity.

3. **Investigation history should be tamper-evident.**
   Investigation events are hash-chained so modification, reordering, or removal within a preserved sequence can be detected.

4. **Ledger completeness requires an independently preserved checkpoint.**
   A valid internal hash chain alone cannot prove that the end of a ledger was not removed. Checkpoints bind an expected event count and ledger head hash.

5. **AI involvement must be observable without recording private chain-of-thought.**
   AI provenance records should preserve operationally relevant inputs, evidence references, model identity, tool activity, outputs, and analyst disposition—not hidden reasoning.

6. **Verification claims must not exceed the trust model.**
   Hash chains and checkpoints provide integrity evidence. They do not by themselves prove legal admissibility, prevent an attacker with full write access from rewriting all records, or establish legal chain of custody.

## 2. Core Investigation Objects

### EvidenceArtifact

`EvidenceArtifact` represents the integrity identity of acquired or derived evidence.

At minimum, an artifact records:

* case identifier
* artifact identifier
* SHA-256 content digest
* media type when known
* source name or source reference
* acquisition timestamp when available
* classification when applicable
* bounded metadata

The content SHA-256 represents the evidence bytes.

The record integrity identifier represents the canonical metadata record describing those bytes.

These are intentionally separate concepts.

Two evidence records may describe the same byte content while carrying different acquisition or provenance metadata.

---

### EvidenceRelationship

`EvidenceRelationship` represents lineage between artifacts.

Examples include:

* acquired-from
* extracted-from
* normalized-from
* decoded-from
* rendered-from
* enriched-from
* summarized-from
* derived-from

A relationship may also identify:

* transformation name
* transformation version
* actor or tool
* creation timestamp
* bounded transformation metadata

Evidence lineage must not imply that a derived representation is identical to its parent.

---

### InvestigationEvent

`InvestigationEvent` represents a consequential event in the investigation.

Expected event classes include, but are not limited to:

* `EVIDENCE_ACQUIRED`
* `EVIDENCE_HASHED`
* `EVIDENCE_PARSED`
* `EVENT_NORMALIZED`
* `PACK_EXECUTED`
* `FINDING_CREATED`
* `MODEL_INVOKED`
* `TOOL_INVOKED`
* `ANALYST_REVIEWED`
* `FINDING_ACCEPTED`
* `FINDING_REJECTED`
* `CONTAINMENT_REQUESTED`
* `CONTAINMENT_COMPLETED`
* `CASE_CLOSED`

Each event includes:

* sequence
* case identifier
* event type
* timestamp
* actor
* payload
* previous-event hash
* current-event hash

The previous-event hash creates the investigation ledger chain.

---

### InvestigationLedger

`InvestigationLedger` is an ordered sequence of investigation events.

Verification must detect:

* modified event content
* invalid event hash
* modified previous hash
* sequence gaps
* event reordering
* case identifier mismatch
* middle-event deletion

The ledger must be treated as append-oriented investigation history.

Hash chaining makes changes detectable when the expected chain state is known. It does not prevent an attacker with sufficient write access from rewriting every event and recomputing the complete chain.

---

### LedgerCheckpoint

`LedgerCheckpoint` binds a known investigation state to:

* case identifier
* event count
* ledger head hash
* checkpoint creation time
* canonicalization method
* hash algorithm
* schema identifier

A checkpoint enables detection of ledger tail truncation.

For example, if an investigation previously contained 100 events and an attacker removes events 91 through 100, the remaining 90-event chain may still be internally valid. Validation against the preserved checkpoint must fail because the event count and head hash no longer match.

The checkpoint exposes a `checkpoint_hash` suitable for later signing or external anchoring.

A checkpoint hash is **not itself an external trust anchor**.

A party able to replace both the ledger and its checkpoint could recompute both.

A later v1.7 milestone will support cryptographically signed or externally anchored checkpoints.

## 3. Canonicalization and Hashing

Investigation-integrity objects use:

* **RFC 8785 JSON Canonicalization Scheme**
* **SHA-256**

Canonicalization must occur before record hashing.

This prevents integrity identities from depending on Python dictionary insertion order, whitespace, indentation, platform newline behavior, or ordinary JSON serialization differences.

RFC 8785 also makes independent verification by implementations written in other languages practical.

The current algorithm identifier is `sha256`.

Future schemas should preserve algorithm agility rather than assuming SHA-256 can never change.

## 4. AI Provenance

`AIProvenanceRecord` records operationally relevant AI participation in an investigation.

Useful provenance may include:

* provider
* model identifier
* model version when available
* provider request or invocation identifier
* execution timestamp
* policy or configuration identifier
* evidence references
* retrieval references
* tool calls
* structured output
* confidence or uncertainty when meaningful

AI provenance must not become an uncontrolled sensitive-data archive.

AI-DFIR should avoid storing by default:

* private model chain-of-thought
* secrets
* authentication material
* unnecessary full prompts
* unnecessary PHI or PII
* unrelated conversation history

Where full context cannot safely be retained, provenance may reference preserved evidence objects or cryptographic hashes instead.

AI-generated conclusions are derived investigative material, not source evidence.

---

## 5. Analyst Decision Provenance

`AnalystDecisionRecord` records human disposition of consequential investigative findings.

Examples include:

* confirmed
* rejected
* accepted with qualification
* escalated
* containment approved
* containment denied
* investigation closed

A decision may reference:

* analyst identity
* target finding or action
* decision timestamp
* evidence references
* rationale

Human decisions must remain distinguishable from AI recommendations.

An AI recommendation becoming an analyst-approved decision is itself an important investigation transition.

## 6. Investigation Replay

v1.7 should support reconstruction of investigation activity from preserved artifacts.

Replay has two modes conceptually:

### Deterministic replay

Used for deterministic AI-DFIR components such as:

* parsers
* normalizers
* Evidence Pack evaluation
* hashing
* lineage construction
* rule-based detectors
* case verification

Given the same preserved inputs and configuration, these components should reproduce the same result.

### Recorded AI replay

Model output must not be assumed to be reproducible merely because the same prompt and model name are available.

For AI activity, investigation replay should preserve and display the original:

* request metadata
* evidence/context references
* tool activity
* recorded structured response
* output digest
* resulting analyst disposition

A later live model invocation is a **new comparison execution**, not proof that the original stochastic model response has been reproduced.

---

## 7. Case Verification

A future v1.7 case verifier should support an offline workflow conceptually equivalent to:

`ai-dfir verify-case <case>`

Verification should eventually validate:

* evidence content hashes
* evidence-record identities
* evidence lineage
* investigation-event hashes
* ledger chaining
* sequence continuity
* ledger checkpoint
* AI provenance references
* analyst decision references
* exported file hashes
* case manifest
* optional checkpoint signature or external anchor

Verification should return explicit PASS/FAIL results for individual controls rather than only a single opaque overall result.

The target v1.7 case bundle is expected to contain artifacts such as:

* `CASE_MANIFEST.json`
* `EVIDENCE_MANIFEST.json`
* `INVESTIGATION_LEDGER.jsonl`
* `LEDGER_CHECKPOINT.json`
* `TIMELINE.jsonl`
* `FINDINGS.json`

* `ANALYST_DECISIONS.jsonl`
* `CUSTODY_RECORD.jsonl`
* `VALIDATION_REPORT.json`
* `SHA256SUMS`
* investigator-readable report output

Not every file must be introduced in the first v1.7 milestone.

The architecture should evolve toward this bundle without breaking earlier AI-DFIR case semantics.

## 9. Trust Boundaries and Limitations

The investigation integrity layer is designed to provide strong evidence of consistency and alteration.

It must not be described as providing guarantees it does not possess.

Specifically:

* A hash chain is tamper-evident, not tamper-proof.
* A checkpoint detects truncation only when the expected checkpoint is preserved independently from the altered ledger.
* An unsigned checkpoint can be replaced by an attacker who controls both ledger and checkpoint storage.
* Cryptographic integrity does not establish that the original data source was truthful.
* Cryptographic integrity does not establish legal admissibility.
* AI provenance does not make AI output factual.
* Synthetic validation results do not establish production false-positive or false-negative rates.
* Investigation assurance does not replace organizational evidence-handling procedures.

When legal process has not established a formal chain of custody, AI-DFIR documentation should prefer terms such as **evidence integrity**, **evidence lineage**, **custody record**, and **investigation provenance**.

## 10. Security Requirements

v1.7 investigation-assurance components must:

* avoid modifying source evidence during analysis
* reject unsupported or malformed integrity records
* bound untrusted metadata where appropriate
* avoid secrets in provenance records
* use explicit UTF-8 handling for text artifacts
* use deterministic canonicalization for hashed objects
* keep signing keys outside the repository
* distinguish source evidence from derived findings
* preserve algorithm and schema identifiers
* support offline verification
* fail closed when required integrity relationships cannot be verified

## 12. Compatibility Requirement

v1.7 must not regress established AI-DFIR behavior.

During development:

* the existing Evidence Pack catalog remains intact
* the 111-pack validation baseline remains green
* existing synthetic detector-domain validation remains green
* earlier compatibility tests remain green
* v1.6 release-assurance controls remain in force unless explicitly superseded by a stronger control

New Evidence Packs are not required to prove the value of v1.7.

The first v1.7 objective is to make the **investigation itself verifiable**.
