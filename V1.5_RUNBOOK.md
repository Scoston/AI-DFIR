# AI-DFIR v1.5 — Release, Deployment & Investigation Runbook

## Purpose

AI-DFIR v1.5 is a defensive AI-specific DFIR reference platform. It preserves and correlates evidence across model integrity, runtime state, agent execution, RAG/memory, tools/MCP/A2A, representation attacks, workload identity, temporal authority, provider telemetry, evidence custody, containment, and downstream consequences.

The platform is designed around four rules:

1. **Missing evidence is unknown, never clean.**
2. **Presence is not quality; important evidence must be integrity-bound.**
3. **Correlation is not causation.**
4. **High-impact containment, attribution and closure remain human-controlled decisions.**

## Start a case

```bash
python case_init.py --case-id CASE-001 --root /analysis
```

Preserve raw evidence before normalization. When acquiring evidence, capture source identity, host/workload, incident-window coverage, clock quality, collection method, SHA-256, and collector authorization.

## Analyst workflow

1. Confirm incident scope, tenant, legal authority and time window.
2. Acquire original/raw evidence and validate chain of custody.
3. Select the relevant Evidence Pack(s).
4. Record evidence quality and collection gaps before interpreting findings.
5. Build the event/authority/causal graph.
6. Correlate with independent target-system/provider evidence.
7. Preserve suspect runtime state before containment when operationally safe.
8. Reconcile downstream consequences after containment.
9. Require independent review for high-impact attribution and closure.
10. Export a signed/redacted case package only after validation.

Use `docs/analyst/ANALYST_QUICKSTART.md`, `INCIDENT_WORKFLOW.md`, and `HUMAN_IN_THE_LOOP.md` during live analysis.

## Workbench

The Analyst Workbench is read-only by design and defaults to local access. Do not expose it directly to the Internet. Put remote deployments behind the authenticated enterprise gateway/reverse proxy, mTLS, tenant RBAC and audit logging.

## Enterprise deployment sequence

1. PostgreSQL metadata backend with RLS/FORCE RLS.
2. OIDC or signed normalized enterprise identity; SPIFFE/mTLS for service identity.
3. KMS/HSM-backed envelope encryption.
4. Immutable/WORM object storage.
5. Legal-hold enforcement.
6. Distributed collector enrollment and signed acquisition tasks.
7. Provider-native collector permissions and retention verification.
8. Backup/restore and DR validation.
9. Analyst audit, peer review and redaction controls.
10. Production-readiness evidence gate.

See `docs/deployment/` for platform-specific guides.

## Human-in-the-loop gates

A human investigator/authorized incident commander should approve or independently review:

- acquisition that touches sensitive or privileged sources;
- collection of process memory or decrypted/secrets-bearing content;
- disruptive containment, failover, credential revocation or deletion;
- causal attribution where explicit evidence is incomplete;
- conclusions about malicious intent;
- legal-hold release;
- case closure;
- external sharing/export of evidence.

Automation may prioritize, normalize and detect. It should not silently convert uncertainty into fact.

## Operational limitations

The reference package cannot prove your enterprise controls are correct merely because configuration files exist. Production readiness requires organization-specific testing of IdP, SPIFFE trust roots, KMS/HSM, PostgreSQL HA/RLS, immutable object storage, retention, provider APIs, backup/restore, network controls and authorization boundaries.
