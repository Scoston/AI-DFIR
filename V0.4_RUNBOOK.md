# AI-DFIR Model Integrity v0.4 — Execution Provenance & Incident Reconstruction

## Purpose

v0.4 expands the Qwen3.8 forensic detector into a broader AI execution-forensics framework.

The investigation target is the whole execution stack:

```text
model weights
+ adapters
+ tokenizer/chat template
+ system configuration
+ serving code
+ runtime hooks
+ hardware trust
+ retrieval/tool activity
+ activation behavior
= actual AI execution
```

The goal is not to label a model "abliterated" from one suspicious answer. The goal is to reconstruct and correlate evidence well enough to support a defensible model-integrity finding.

## v0.4 major additions

- Ed25519-signed DSSE/in-toto-style execution provenance bundles
- known-good statistical runtime baselines
- automatic residual-depth divergence localization
- live model-object hook/adapter/config inventory
- controlled approved-vs-suspect replay
- model-adapter registry (Qwen3.8 + generic fallback)
- hash-first agent/tool/retrieval/consequence traces
- optional eBPF runtime file/exec/connect collection
- GPU/hardware attestation evidence ingestion
- normalized forensic timeline builder
- OCSF 1.8-aligned AI operation export
- multi-source evidence correlation / confidence levels

## Standards basis

v0.4 deliberately distinguishes standards-aligned packaging from custom forensic semantics.

- in-toto Statement v1 / DSSE concepts are used for signing the custom AI-DFIR execution predicate.
- SLSA v1.2 concepts inform provenance and verification, but an AI inference is **not** mislabeled as SLSA build provenance.
- OCSF 1.8.0 is the stable export target; it introduced the `ai_operation` profile, `ai_model`, `message_context`, and GPU information support.
- NVIDIA attestation evidence can be ingested after verification by vendor-supported tooling. Current NVIDIA documentation recommends its C++ attestation SDK for new deployments.

## 2. Preserve runtime evidence

If the inference worker is still running, collect volatile evidence first:

```bash
sudo bash collect_runtime_linux.sh \
  --pid <MODEL_PID> \
  --out /evidence/CASE-001/01_runtime/basic
```

Optional external observer:

```bash
sudo bash collect_runtime_ebpf.sh \
  --pid <MODEL_PID> \
  --duration 120 \
  --out /evidence/CASE-001/01_runtime/ebpf
```

The eBPF collector observes `openat`, `execve`, and `connect` syscalls for the selected PID. It is optional and requires `bpftrace`.

## 3. Establish the approved reference

Always use the exact approved commit/revision:

```bash
python download_reference.py \
  --repo Qwen/Qwen3.8-27B \
  --revision <FULL_APPROVED_COMMIT_SHA> \
  --out /evidence/CASE-001/03_reference/qwen38
```

## 4. Run static checkpoint analysis

```bash
python qwen_forensic_detector.py full \
  --reference /evidence/CASE-001/03_reference/qwen38 \
  --suspect /evidence/CASE-001/02_suspect \
  --out /evidence/CASE-001/04_static_analysis
```


## 5. Build the approved activation fingerprint

```bash
python activation_fingerprint.py extract \
  --model /evidence/CASE-001/03_reference/qwen38 \
  --local-files-only \
  --prompts prompts/activation_probe.jsonl \
  --thinking off \
  --dtype bf16 \
  --out /evidence/CASE-001/05_approved_activations
```

Then:

```bash
python activation_fingerprint.py derive \
  --approved-activations /evidence/CASE-001/05_approved_activations \
  --out /evidence/CASE-001/06_fingerprint
```

## 6. Capture live execution attestation

For standalone controlled probes:

```bash
export QWEN_ATTESTATION_HMAC_KEY_HEX='<secret hex key>'

python live_attestation.py probe \
  --model /evidence/CASE-001/02_suspect \
  --local-files-only \
  --fingerprint /evidence/CASE-001/06_fingerprint \
  --approved-activations /evidence/CASE-001/05_approved_activations \
  --prompts prompts/activation_probe.jsonl \
  --thinking off \
  --depths 16,24,32,36,40,44,48,56,64 \
  --log /evidence/CASE-001/08_live_attestation/events.jsonl \
  --head /evidence/CASE-001/08_live_attestation/chain_head.json
```

For a true runtime-only intervention, integrate `PassiveActivationAttestor` into the already-running production worker using `production_integration_example.py`.

## 7. Inventory the live Python model object

Inside an approved deployment, capture a known-good runtime inventory using:

```text
runtime_model_inventory_example.py
```

Do the same on the suspect worker.

Then compare:

```bash
python runtime_inventory.py compare \
  --approved approved_runtime_inventory.json \
  --suspect suspect_runtime_inventory.json \
  --out /evidence/CASE-001/01_runtime/runtime_findings.json
```

This specifically compares:
- config fingerprint
- registered forward/pre/backward hooks
- active adapters
- PEFT adapter configuration

## 8. Build a known-good statistical baseline

Use multiple approved live-attestation runs:

```bash
python baseline_engine.py build \
  --log approved-run-01.jsonl \
  --log approved-run-02.jsonl \
  --log approved-run-03.jsonl \
  --log approved-run-04.jsonl \
  --out /evidence/CASE-001/09_baselines/approved_runtime_baseline.json
```

Score the suspect:

```bash
python baseline_engine.py score \
  --baseline /evidence/CASE-001/09_baselines/approved_runtime_baseline.json \
  --log /evidence/CASE-001/08_live_attestation/events.jsonl \
  --z-threshold 5 \
  --min-consecutive 2 \
  --out /evidence/CASE-001/09_baselines/suspect_score
```

The localizer works with sparse selected depths. "Consecutive" means consecutive **observed** depths, not numeric `depth + 1`.

Outputs:

```text
anomaly_events.csv
divergence_report.json
divergence_report.md
```

## 9. Controlled forensic replay

Replay the same test set against approved and suspect checkpoint states:

```bash
python replay_engine.py \
  --approved-model /evidence/CASE-001/03_reference/qwen38 \
  --suspect-model /evidence/CASE-001/02_suspect \
  --prompts prompts/activation_probe.jsonl \
  --thinking off \
  --dtype bf16 \
  --out /evidence/CASE-001/10_replay
```

This produces a layer-by-layer approved-vs-suspect differential.

**Limitation:** a clean-lab replay cannot reproduce an attack that existed only as an in-memory production hook unless that runtime state is reconstructed.

## 10. Trace agent/tool/retrieval consequences

Example:

```bash
python agent_trace.py \
  --log /evidence/CASE-001/11_agent_trace/trace.jsonl \
  --inference-id INF-123 \
  --type tool_call \
  --name disable_user \
  --content '{"user":"example"}' \
  --authority-id delegation-42
```

The supplied content is hashed; plaintext is not written to the trace.

Available event types:

```text
decision
retrieval
tool_call
tool_result
delegation
consequence
containment
```

This allows investigators to track what escaped the model boundary before containment.

## 11. Hardware/GPU attestation

Use the vendor-supported hardware attestation workflow first.

Then preserve the returned token/verifier evidence:

```bash
python gpu_attestation_ingest.py \
  --token-file nras_token.jwt \
  --verifier-output nvat_verifier_output.json \
  --verification-status verified \
  --out /evidence/CASE-001/12_hardware_attestation/gpu_attestation.json
```

Important:

`gpu_attestation_ingest.py` does not claim that decoding a JWT verifies the signature. It records the raw token hash and externally established verification state.

## 13. Export to OCSF

```bash
python ocsf_export.py \
  --attestation-log /evidence/CASE-001/08_live_attestation/events.jsonl \
  --model-name Qwen3.8-27B \
  --model-provider Qwen \
  --schema-version 1.8.0 \
  --out /evidence/CASE-001/14_ocsf/ai_runtime_events.jsonl
```

The exporter maps to OCSF Process Activity with the `ai_operation` profile and carries AI-DFIR-specific measurements in `unmapped`.

Use an OCSF validator in production pipelines requiring strict conformance.

## 14. Correlate the evidence

```bash
python correlate_evidence.py \
  --divergence-report /evidence/CASE-001/09_baselines/suspect_score/divergence_report.json \
  --tensor-metrics /evidence/CASE-001/04_static_analysis/tensor_metrics.csv \
  --low-rank-screen /evidence/CASE-001/04_static_analysis/low_rank_screen.csv \
  --runtime-findings /evidence/CASE-001/01_runtime/runtime_findings.json \
  --timeline-json /evidence/CASE-001/13_timeline/timeline.json \
  --out /evidence/CASE-001/16_reports/evidence_correlation.json
```

Confidence levels:

```text
Level 1 — behavioral/mechanistic anomaly
Level 2 — artifact/runtime anomaly
Level 3 — mechanistic + artifact/runtime correlation
Level 4 — provenance/timeline + mechanistic correlation
```

The correlator intentionally does not treat any single signal as proof of abliteration.

## 15. Create a signed execution-provenance bundle

Generate an investigator signing key:

```bash
python provenance_bundle.py keygen \
  --private investigator_ed25519.pem \
  --public investigator_ed25519.pub.pem
```

Protect the private key.

Bundle the case evidence:

```bash
python provenance_bundle.py bundle \
  --case-id CASE-001 \
  --inference-id INF-123 \
  --private-key investigator_ed25519.pem \
  --model Qwen3.8-27B \
  --model-revision <DEPLOYED_REVISION> \
  --material reference_manifest=/evidence/CASE-001/03_reference/FORENSIC_REFERENCE_PROVENANCE.json \
  --artifact static=/evidence/CASE-001/04_static_analysis \
  --artifact live=/evidence/CASE-001/08_live_attestation \
  --artifact timeline=/evidence/CASE-001/13_timeline \
  --artifact report=/evidence/CASE-001/16_reports/evidence_correlation.json \
  --gpu-attestation /evidence/CASE-001/12_hardware_attestation/gpu_attestation.json \
  --tool-trace /evidence/CASE-001/11_agent_trace/trace.jsonl \
  --out /evidence/CASE-001/15_provenance_bundle
```

Verify:

```bash
python provenance_bundle.py verify \
  --bundle /evidence/CASE-001/15_provenance_bundle \
  --public-key investigator_ed25519.pub.pem
```

The package contains:

```text
evidence_manifest.json
statement.json
attestation.dsse.json
signing_public_key.pem
BUNDLE_HEAD.json
evidence/
```

## 16. Recommended finding language

Avoid:

> The model was definitely abliterated because it answered a prohibited prompt.

Prefer:

> The deployed AI execution materially diverged from the approved baseline beginning at residual depth X. The divergence correlates with [unauthorized runtime hook / checkpoint tensor changes / adapter state], and the relevant change was introduced at approximately [time] according to preserved runtime evidence. The combined evidence supports a Level N model-integrity finding.

Only attribute the exact modification technique when the evidence supports it.
