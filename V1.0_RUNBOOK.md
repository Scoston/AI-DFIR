# AI-DFIR v1.0 — Enterprise AI Incident Response Platform

## What v1.0 adds

v1.0 turns the v0.1-v0.9 forensic stack into a centrally governed incident
response system.

New enterprise functions:

```text
central case lifecycle
RBAC
tenant isolation
classification controls
SSO/reverse-proxy authentication boundary
encrypted content-addressed evidence repository
deduplication
legal hold
retention/disposition planning
signed repository checkpoints
signed distributed collectors
verified central ingest
evidence acquisition tasking
signed detection/evidence content releases
enterprise portal/API
SOC/SIEM exports
closure-readiness gate
reference systemd/Docker deployment
```

All v0.1-v0.9 tooling remains in the package.

# 2. Initialize enterprise storage

Generate a random 32-byte repository encryption key using your approved secret
management process.

For a lab only:

```bash
python -c 'import secrets; print(secrets.token_hex(32))'
```

Initialize:

```bash
python evidence_repository.py init \
  --root /var/lib/ai-dfir/repository \
  --key-hex "$AI_DFIR_REPOSITORY_KEY_HEX"
```

The key is not stored in the repository.

Create/open the case database by starting the API or importing `CaseDB`.

---

# 3. Identity and SSO boundary

v1.0 intentionally does not implement an IdP.

Place the API/portal behind an enterprise identity-aware reverse proxy that:

1. validates OIDC/SAML/MFA,
2. maps directory groups to AI-DFIR roles,
3. creates claims,
4. HMAC signs the claims.

Claims:

```json
{
  "sub": "analyst@example.com",
  "role": "senior_analyst",
  "tenant_id": "health-plan-a",
  "groups": ["AI-IR"],
  "exp": 1780000000
}
```

Reference helper:

```bash
python trusted_auth_context.py sign \
  --secret-hex "$AI_DFIR_AUTH_SECRET_HEX" \
  --claims-json '{"sub":"analyst@example.com","role":"senior_analyst","tenant_id":"health-plan-a"}'
```

Never expose the API directly to an untrusted network.

# 7. Distributed collector enrollment

Create collector identity:

```bash
python fleet_crypto.py keygen \
  --private collector-01.pem \
  --public collector-01.pub.pem
```

Initialize registry:

```bash
python collector_registry.py init \
  --registry /etc/ai-dfir/collectors.json
```

Enroll collector for specific tenant(s):

```bash
python collector_registry.py enroll \
  --registry /etc/ai-dfir/collectors.json \
  --collector-id collector-01 \
  --public-key collector-01.pub.pem \
  --tenant health-plan-a
```

Collectors cannot submit evidence for other tenants.

# 8. Build a collector evidence bundle

```bash
python collector_bundle.py create \
  --out /staging/bundle-001 \
  --collector-id collector-01 \
  --case-id AIIR-20260823-1234abcd \
  --tenant-id health-plan-a \
  --private-key collector-01.pem \
  --file 'AlertInfo.json=/acquisition/AlertInfo.json::confidential' \
  --file 'session.jsonl=/acquisition/session.jsonl::restricted'
```

The bundle cryptographically binds:

```text
collector
tenant
case
each file name
size
classification
SHA-256
```

# 9. Verify and ingest

```bash
python enterprise_ingest.py \
  --bundle /staging/bundle-001 \
  --registry /etc/ai-dfir/collectors.json \
  --cases-db /var/lib/ai-dfir/cases.db \
  --repository /var/lib/ai-dfir/repository \
  --repository-key-hex "$AI_DFIR_REPOSITORY_KEY_HEX" \
  --actor collector-ingest
```

Ingest fails when:

```text
collector signature is invalid
collector is disabled
tenant isn't authorized
bundle tenant != case tenant
file missing
size changed
SHA-256 changed
case doesn't exist
```

# 10. Repository semantics

The first copy of content is stored by SHA-256.

If five alerts contain the same evidence file:

```text
5 evidence records
1 physical CAS object
```

Each evidence record still retains its own:

```text
case
logical name
source
classification
acquisition time
metadata
retention deadline
```

```python
repo.create_hold(
```


```bash
  --root /var/lib/ai-dfir/repository \
  --key-hex "$AI_DFIR_REPOSITORY_KEY_HEX"
```

```bash
python repository_checkpoint.py create \
  --repository /var/lib/ai-dfir/repository \

  --out checkpoint-2026-08-23.json
```

Store signed checkpoints in a separate security/WORM trust domain.

# 17. Signed detection/evidence content releases

Create content-signing key:

```bash
python fleet_crypto.py keygen \
  --private content_release.pem \
  --public content_release.pub.pem
```

Build release:

```bash
python content_pack_manager.py build \
  --out /releases/ai-dfir-content-1.0.0 \
  --private-key content_release.pem \
  --version 1.0.0
```

Verify before promotion:

```bash
python content_pack_manager.py verify \
  --release /releases/ai-dfir-content-1.0.0 \
  --public-key content_release.pub.pem
```

This protects the detection/evidence requirements themselves from silent
modification.

# 19. Closure gate

Before incident closure:

```bash
python closure_gate.py \
  --workspace /analysis/AIIR-... \
  --repository /var/lib/ai-dfir/repository \
  --repository-key-hex "$AI_DFIR_REPOSITORY_KEY_HEX" \
  --out closure_readiness.json
```

Potential blockers:

```text
mandatory evidence missing
open downstream consequences
containment still active
repository integrity failure
```

Unsupported conclusion gates are reported as warnings.

Organizations can decide whether a formally approved waiver is required for
specific missing evidence.

# 21. Standards position

v1.0 targets OCSF 1.8.0 for current security-event interoperability.

OCSF 1.8 added the `ai_operation` profile, `ai_model`, `message_context`,
`token`, GPU and privilege-related structures.

OpenTelemetry remains useful for operational observability, but semantic
conventions are allowed to evolve independently of the forensic source of
record.

The signed AI-DFIR repository remains the evidentiary system of record.
